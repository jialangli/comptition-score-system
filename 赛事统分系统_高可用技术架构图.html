赛事统分系统 · 高可用技术架构（双重保险）

针对「赛场 Wi-Fi 不可靠 / 中央服务器单点故障」的四层冗余设计。核心原则：提交先落本地、后台异步同步、主备无感切换、极端情况纸质兜底，确保网络崩了也打得完分、丢不了分。

LAYER 0 终端层 裁判平板 / 记分员 PC · 本地优先

裁判端离线 PWA Client

  • 本地权威库 IndexedDBscore_records（打分记录）· op_log（操作日志）· sync_state（待同步标记）
  • Service Worker：静态资源离线缓存，断网也能打开 App
  • 提交状态机：草稿 → 本地已存 ✓ → 同步中 → 已同步（服务器 ACK）→ 失败回退本地
  • 双态徽标：● 本地已存 · 已同步 断网时显示本地态

记分员端 PC Client

  • 同构本地库 + 服务器健康看板主/备在线态 · 复制延迟 · 待同步队列数
  • 应急模式开关：正常 / 本地+纸质
  • 赛后应急补录通道：带标记，区分正式/应急数据
机制 · 本地优先提交
写本地(瞬时)返回成功后台异步 POST服务器 ACK标记已同步
网络异常 → 留本地队列，恢复后自动重发；平板断电/刷新不丢（IndexedDB 持久化）。
打分数据 · 增量同步
LAYER 1 同步层 增量同步网关 · 冲突 / 续传

增量同步网关 Edge

  • op-log 拉取：基于 checkpoint 的增量同步，断点续传（offset 记录）
  • 冲突检测：version（版本号）+ timestamp高版本胜 · 同版本以服务器权威 · 疑似冲突标记「待仲裁」
  • 双链路探测：主 Wi-Fi / 应急热点，应用层选优；写失败入本地队列
  • 重试策略：指数退避，最多 N 次后转人工提示
机制 · 冲突解决
每条目带 (version, timestamp)：
• version 高者胜；version 相同 → 服务器权威
• 同队同轮收到 2 份不同成绩 → 标待仲裁，进 S5 人工裁决
• 所有覆盖写写入不可变审计日志(WORM)
HTTP · 写主读主 · 心跳探测
LAYER 2 服务层 主备双服务器 · 自动 Failover

主服务器 192.168.1.10

  • 应用服务 + 主 DB（读写）
  • 对外暴露虚拟 IP（VIP），终端始终连 VIP
  • WAL/binlog 异步流复制到备

备服务器 192.168.1.11

  • 应用服务 + 备 DB（副本，待升主）
  • 实时接收主库复制流，复制延迟监控
  • 心跳失联时 升主 并接管 VIP
机制 · 心跳 & Failover
心跳：3s/次，连续 3 次失联 → 判定故障
Failover：VIP 漂移到备，RTO <10s，终端无感切换
所有切换事件写入不可变审计日志(WORM)
双链路 · 任一通即可服务
LAYER 3 网络层 双网络冗余

主链路 · 赛场 Wi-Fi SSID WRC-Score

  • 场馆部署的专用无线，独立供电 AP
  • 承载常态所有平板 / PC 流量

备链路 · 应急热点 SSID WRC-Failover

  • 4G/5G 应急热点，与主 Wi-Fi 物理隔离
  • 路由器 / AP 独立 UPS 供电
  • 主链路断 → 应用层自动切备，无需人工
灾难级断网 · 降级到本地+纸质
LAYER 4 兜底层 应急模式 · 纸质对账

应急模式 / 纸质对账 Fallback

  • 一键切换「本地 + 纸质」：预印每队纸质打分表
  • 灾难级断网：人工打分 → 赛后应急补录通道录入
  • 数据收敛：恢复后增量同步 + 补录合并，最终一致
机制 · 数据收敛
应急数据带 is_emergency 标记，
与正式库合并去重（按 (team,round) 主键），
赛后生成差异报告供裁判长复核。
可观测性监控（横切） 健康看板数据源：服务器在线态 / 复制延迟 / 待同步队列长度 / 双链路状态 监控告警：主备失联 / 复制延迟超阈 / 待同步队列积压 → 记分员端提示
不可变审计日志WORM · 横切

性质 · Write-Once-Read-Many

  • append-only：任何记录不可修改、不可删除，仅可追加
  • 主备双写 + 随 WAL 复制；终端 IndexedDB 本地审计队列同步时一并上传
  • 可选哈希链防篡改：每条 hash = H(prev_hash + content)，篡改即检出

记录事件（写入点）

  • 每条打分提交（本地→同步状态、version、source）
  • 同步 / 补传（offset、成败）
  • 冲突解决（胜方 version、被覆盖原值）
  • Failover 切换、应急模式开关、补录（is_emergency 标记、操作人）
  • 任何覆盖写 / 修正（before→after、理由）

字段 & 用途

  • event_id/op_type/entity(team,round)/before/after/actor/ts/version/source
  • 用途：赛后复盘 · 争议追溯 · 合规定责 · 与 L4 差异报告对账
故障切换时序 · 四种典型场景
SCENARIO 1
平板断网
提交写本地 ✓本地已存，后台重试同步；恢复后自动补传，不打断裁判。
SCENARIO 2
主服务器宕
心跳失联 → VIP 漂到备 → 终端无感切换，打分不中断（RTO<10s）。
SCENARIO 3
双网络断
全本地模式 + 纸质兜底，数据暂存本地，待网络恢复再收敛。
SCENARIO 4
全面恢复
增量同步 + 补录合并 → 数据收敛一致，审计留痕，出差异报告。
